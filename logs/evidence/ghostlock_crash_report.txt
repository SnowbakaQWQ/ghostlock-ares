【三】崩溃点归类分析
================================================================================

■ 类型 A —— 崩溃在 futex 自身的清理路径

    el0_svc_naked
      -> SyS_futex
      -> do_futex
      -> futex_lock_pi
      -> rt_mutex_cleanup_proxy_lock
      -> remove_waiter                 <<< 在这里 fault
      -> rt_mutex_adjust_prio_chain
      -> el1_da  (data abort)

    含义: remove_waiter() 内部会调用 rt_mutex_adjust_prio_chain 去调整 PI 链，
          此时读到被写坏的 waiter->lock / rb 节点，直接踩空。
          属于「stamp 把 waiter 写坏了」的表现。

■ 类型 B —— 崩溃在 sched_setattr 触发的 PI walk

    el0_svc_naked
      -> SyS_sched_setattr
      -> __sched_setscheduler
      -> rt_mutex_adjust_pi
      -> rt_mutex_adjust_prio_chain
      -> _raw_spin_trylock            <<< 在这里 fault
      -> el1_da  (data abort)

    含义: PI walk 成功进入了（说明 early-return 已被绕过，
          waiter->prio != task->prio 这个条件成立了）。
          随后 _raw_spin_trylock 去锁 waiter->lock 指向的地址，该地址不可访问。

■ 关键判断

  1) 类型 B 的出现，证明 stamp 确实落到了 waiter 结构体上，
     PI walk 也确实被触发。也就是说「打不中」的问题已经解决。

  2) 现在的问题变成：「打中了，但 lock 指针指向无效内存」。
     这正是接下来要做的事：让 lock 指向一块真实可控的内存（如 pipe_buffer / ashmem），
     而不是 0xdeadbeef 这类探测值。

  3) 早期记忆里认为「崩溃在 sendmsg 返回路径」——从 AEE 实测栈看并不成立。
     真实崩溃点始终在 rt_mutex 的 PI 链遍历内部。
